# RoofTop Food Delivery

Assigns delivery boys to customer orders for the RoofTop restaurant, exposed as a Spring
Boot REST service backed by MySQL.

## Problem

N customers order lunch. M delivery boys are available. Each customer has an order time `O`
and a travel time `T` from the restaurant. A delivery boy carries one order at a time and
takes the next order as soon as he is back. The lowest numbered free driver is always used.
If nobody is free the order is refused with `No Food :-(`.

## Business rules

1. Orders are handled in ascending order time. A tie goes to the lower customer number.
2. A driver is free for an order when `availableAt <= orderTime`.
3. Of the free drivers, the lowest number wins.
4. An assigned driver is free again at `orderTime + travelTime`.
5. If nobody is free the order is refused and no driver state changes.

Rule 2 needs the `<=`. In the sample input C5 is placed at minute 24 and D2 returns at
minute 24, so a strict comparison gives the wrong answer for that order.

The problem does not say how to break a tie on order time. Lower customer number first is
the assumption taken, fixed in `DriverAssignmentEngine` so a run is deterministic.

## Sample input and output

Input is `6,2` — six customers, two drivers — followed by the `(O, T)` pairs:

```
1,10
4,20
15,5
22,20
24,10
25,10
```

Output:

```
C1 - D1
C2 - D2
C3 - D1
C4 - D1
C5 - D2
C6 - No Food :-(
```

Each driver's return minute as the orders are handled:

```
           D1   D2
start       0    0
C1 (1,10)  11    0
C2 (4,20)  11   24
C3 (15,5)  20   24
C4 (22,20) 42   24
C5 (24,10) 42   34
C6 (25,10) 42   34   -> both out, refused
```

## Architecture

```
REST controller  ->  DeliveryRunService  ->  DriverAssignmentEngine
                            |
                     Spring Data JPA
                            |
                          MySQL
```

The engine holds the allocation rules and nothing else: no clock, no database, no state
between calls. That makes a run reproducible and lets the rules be tested without starting
the application. The service turns the engine's answer into rows inside one transaction.
The controller only handles HTTP.

### Allocation

Two heaps, rather than scanning the whole fleet for every order:

* free drivers — a min-heap on driver number
* busy drivers — a min-heap on return minute

Before an order placed at minute `O`, every busy driver with `availableAt <= O` is moved
into the free heap. The busy heap is ordered by return minute, so this stops at the first
driver still out and never inspects the rest. The free heap is ordered by number, so its
head is the lowest numbered driver able to take the order.

Cost is `O(N log N + N log M)` against `O(N x M)` for a per-order scan. At M = 2 the
difference is irrelevant; it matters once the fleet is large.

## Data model

A run owns its drivers and orders. Without that scope a second run would see the drivers
left busy by the first one, and the same input would produce a different answer.

```
delivery_runs (run_id, driver_count, created_at)
     |
     +-- drivers (driver_id, run_id, driver_index, available_at)
     |
     +-- customer_orders (order_id, run_id, customer_index, order_time,
                          travel_time, driver_id -> drivers, status)
```

Only `available_at` is stored for a driver. Status is computed from it, so no row can be
left reading `BUSY` after the delivery has ended. `customer_orders.driver_id` is null
exactly for a refused order, rather than a magic value.

The schema lives in `src/main/resources/schema.sql` and is owned by that file, not
generated by Hibernate (`ddl-auto=none`).

## API

| Method | Path | Purpose |
| ------ | ---- | ------- |
| POST | `/api/v1/delivery-runs` | allocate a set of orders, returns 201 |
| GET | `/api/v1/delivery-runs/{runId}` | the stored run as JSON |
| GET | `/api/v1/delivery-runs/{runId}/report` | the run in the required text format |

Swagger UI: `http://localhost:8080/swagger-ui.html`

A run is created in one call because the allocation depends on the whole set of orders and
their order times, not on when the requests happen to arrive. Posting the same input twice
therefore gives the same answer twice.

Request:

```json
{
  "driverCount": 2,
  "orders": [
    {"orderTime": 1,  "travelTime": 10},
    {"orderTime": 4,  "travelTime": 20},
    {"orderTime": 15, "travelTime": 5},
    {"orderTime": 22, "travelTime": 20},
    {"orderTime": 24, "travelTime": 10},
    {"orderTime": 25, "travelTime": 10}
  ]
}
```

Response, trimmed to the first and last order:

```json
{
  "runId": 1,
  "driverCount": 2,
  "orders": [
    {"customerIndex": 1, "orderTime": 1, "travelTime": 10,
     "driverIndex": 1, "status": "ASSIGNED"},
    {"customerIndex": 6, "orderTime": 25, "travelTime": 10,
     "status": "UNASSIGNED", "message": "No Food :-("}
  ],
  "drivers": [
    {"driverIndex": 1, "availableAt": 42, "status": "BUSY"},
    {"driverIndex": 2, "availableAt": 34, "status": "BUSY"}
  ]
}
```

Customers are numbered by their position in the request, so the first order is C1. Driver
status in the response is reported as at the last order time of the run.

## Running

Needs JDK 21 and Maven.

The datasource is configured for MySQL on `localhost:3306`, user `root` with no password.
Adjust the three `spring.datasource.*` lines in
`src/main/resources/application.properties` to match your setup — the database and tables
are created on first start, from the URL's `createDatabaseIfNotExist=true` and from
`schema.sql`.

To run without installing MySQL, swap in the commented H2 block in the same file. H2 runs
in MySQL compatibility mode and executes the same `schema.sql`.

```bash
mvn test
mvn spring-boot:run
```

```bash
curl -X POST http://localhost:8080/api/v1/delivery-runs \
  -H "Content-Type: application/json" \
  -d '{"driverCount":2,"orders":[{"orderTime":1,"travelTime":10},{"orderTime":4,"travelTime":20},{"orderTime":15,"travelTime":5},{"orderTime":22,"travelTime":20},{"orderTime":24,"travelTime":10},{"orderTime":25,"travelTime":10}]}'

curl http://localhost:8080/api/v1/delivery-runs/1/report
```

## Tests

`DriverAssignmentEngineTest` covers the rules directly: the sample input against the exact
expected text, lowest number first, the `availableAt == orderTime` boundary, a refusal
leaving driver state untouched, no drivers at all, unsorted input, a tie on order time, and
a fleet of 100,000 drivers.

`DeliveryRunControllerTest` runs the whole stack over HTTP and the database: the sample
input allocated and stored, the stored run read back in the required format, two runs not
interfering with each other, 404 for an unknown run, and rejected input.

18 tests, verified against MySQL 8.4.9.

## Notes

* Allocation and persistence happen in one transaction, so concurrent requests cannot
  interleave and hand one driver to two orders. Because drivers belong to a run, separate
  runs never contend for the same rows and no row locking is needed. An endpoint that added
  one order at a time to a live run would need `SELECT ... FOR UPDATE` on that run's
  drivers, taken in ascending driver number to avoid deadlock. `SKIP LOCKED` would not be
  safe: it would hand out a higher numbered driver while a lower numbered one is locked,
  breaking rule 3.
* Times are integer minutes because the problem defines `O` and `T` that way. Real
  timestamps and a per-destination travel time would replace them in a production system.
* Delivery is treated as one way, which is what the expected output implies. A round trip
  would only change rule 4 to `orderTime + 2 * travelTime`.
